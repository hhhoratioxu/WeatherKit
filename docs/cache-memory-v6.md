# WeatherKit v6 缓存内存优化

2026-11-01。基线为 `0404e6bf99fb4585d68f032cb2cb09501476bb60`（cache-v5 加 `.lpx` 入口修正）。本次针对缓存写入临时字符串和重新读取缓存时的重复正文，版本为 `3.3.2-cache.6`。

## 实现

旧写法先序列化全部候选记录，超过 256 Ki 字符后逐条移除末尾记录并重新序列化。八条接近正文上限的记录会产生多次远大于最终缓存的字符串。

新写法先计算可保留的前缀，再对最终内容执行一次 `JSON.stringify`。较小缓存使用保守长度上界快速判断；需要精确裁剪时逐个 UTF-16 码元计算转义长度，处理引号、反斜杠、控制字符、有效代理对和孤立代理项，不先分配转义后的完整正文。优先级顺序与旧算法完全一致：遇到放不下的高优先级记录时停止，不跳过它去填入低优先级记录。最终 JSON 的格式、字段顺序和内容与旧写法相同。

缓存写入前仍重新读取存储、合并其他执行的写入。若重新读取的条目与内存条目具有相同身份和正文，则复用已有的不可变字符串，避免继续保留重复解析出的正文；不共享可变的供应商 JSON 对象。

仍最多保留八条内存记录、单条正文 96 Ki 字符、持久化 256 Ki 字符，沿用缓存时效、城市轮换顺序、并发与失败恢复。令牌响应不缓存。只修改 JavaScript 内部处理，Loon 最低版本继续为 3.5.1(983)。2026-11-01 重新核对 [Loon Script API](https://nsloon.app/docs/Script/script_api/) 的同步字符串存储和异步完成约定；没有引入新的宿主 API。

## 测量

运行 `node scripts/measure-cache-memory.mjs` 可复现，[全部 42 个原始样本](cache-memory-v6-measurements.json) 包含源码哈希。使用 macOS arm64、Node v24.22.1；两版源码使用同一个本地 `@noble/hashes` 依赖，没有编译器差异。每个场景每版七个独立进程、交替执行，单样本处理十二次请求。样本在完整 GC 前创建；处理后保持缓存及模拟存储可访问，再进行完整 GC 记录保留堆。以下为中位数。

接近缓存上限的 JSON 样本：

| 指标 | cache-v5 | cache-v6 |
| --- | ---: | ---: |
| 网络请求 / 存储写入 | 12 / 12 | 12 / 12 |
| 完整缓存序列化次数 | 57 | 12 |
| 累计 JSON 输出字符，含身份和元数据 | 31,319,238 | 2,864,727 |
| 最大单次 JSON 字符串长度 | 990,251 | 247,583 |
| 最终持久化字符 / 记录数 | 247,583 / 2 | 247,583 / 2 |
| GC 后保留堆增量 | 1,148,504 B | 776,928 B |
| 采样分配量 | 69,478,872 B | 12,558,384 B |
| 含采样开销的处理耗时 | 62.00 ms | 21.10 ms |

该场景累计 JSON 输出字符减少约 90.9%，GC 后保留堆增量减少约 32.4%，采样分配量减少约 81.9%。最终持久化字节的 SHA-256 相同，全部八条内存记录仍可直接命中。

较小 JSON 场景原本无需裁剪，保留堆约 273 KiB → 279 KiB，采样分配约 930 KiB → 958 KiB；新长度检查存在少量开销，不能称为所有场景都减少内存。大量控制字符的边界样本原先会生成最长 4,321,875 字符的 JSON，新实现提前识别无法写入的记录；两版最终都保留空的磁盘缓存，成功响应与内存命中仍可用。该边界样本不代表正常天气响应。

## 验证和范围

新增测试覆盖全部 65,536 种 UTF-16 单码元、300 组混合转义和代理对样本、恰好容纳与超出一个字符的边界，并与旧序列化算法逐字节比对。实际缓存测试覆盖超限后的命中、单次最终序列化、全部正文无法落盘仍可正常使用；既有跨执行合并、有效期、失败回退与消费者隔离测试继续执行。发布构建与生成文件的验证见 [构建记录](loon-build-validation.json)。

这些结果来自 Node/V8 源码和模拟存储，采样包含测量框架开销，耗时也受采样影响。它们不是 Loon/JavaScriptCore 的原生内存、峰值、VPN 稳定性或耗电测量。正文和存储长度是脚本处理边界，无法限制宿主已经接收的网络缓冲。真实 iPhone 的天气显示、内存与连续运行仍需设备验证。
