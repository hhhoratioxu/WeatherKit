# WeatherKit v7 响应处理内存与 CPU 优化

2026-11-01，版本 `3.3.2-cache.7`。基线是已发布的 `cache-v6`（`1495f2464c792741fe357518fcb2f62b9fb82599`），本次运行脚本来自源码 `c0aa19640e760889de31658df084c176f52d18bd` 的 [GitHub Actions 构建](https://github.com/hhhoratioxu/WeatherKit/actions/runs/41320313790)。

## 改动与行为

- 只把真正改变的数据项传给 FlatBuffer 编码器。比如实况替换成功、小时来源失败时，小时表继续引用原始二进制数据，避免重复创建预报对象和编码缓冲，同时保留当前 schema 尚不认识的字段。
- 预警的深复制延迟到取得可用替换结果之后。等待或来源失败时无需持有第二整份预警；成功合并仍使用隔离副本，不修改原始数据。
- 每条预警只创建一次 schema 视图，读取该记录的字段和 responses 时复用。48 条预警的回归样本确认恰好读取 48 次记录视图。
- 空气质量的 INFO 日志只在 INFO、DEBUG、ALL 级别生成 JSON 字符串，关闭相应日志时跳过字符串化。

保留 v6 缓存字符串优化与此前的按需解码。默认新鲜度、正常预报内容、缓存容量、网络预算、并发和失败恢复沿用原行为；本次不增加后台请求。共享代码的 release 和 development 处理路径同步修改。

2026-11-01 重新核对 [Loon Script API](https://nsloon.app/docs/Script/script_api/) 的二进制正文、同步字符串存储和异步完成约定。继续使用现有原生 API，所有原生回调结束后仅一次 `$done`；最低版本仍为 `3.5.1(983)`，正式入口 `.lpx` 与 `.plugin` 兼容入口内容相同。

## 测量方法

运行 `node --expose-gc scripts/measure-processing-memory.mjs` 可复现。[全部原始样本](processing-memory-v7-measurements.json) 包含两个 CI 产物的 SHA-256、来源提交与逐样本数值。两版包锁除项目版本号外完全一致，发布产物都由 Node v22.23.4 的 CI 使用 `npm ci --ignore-scripts --no-audit --no-fund` 构建。

测量环境为 macOS arm64、Node v24.22.1 / V8，直接执行 CI 压缩脚本，模拟 Loon HTTP 回调和同步存储；没有对真实供应商发出请求。三个场景、两版、CPU 与内存两种模式，每组七个独立进程并交替运行，合计 84 个样本。每个进程执行一次响应脚本。输入样本和 VM 编译在初始 GC 前完成。

CPU 模式不启用内存采样器或运行中 GC；CPU 时间由 `process.cpuUsage` 记录，包含脚本初始化和回调处理。内存模式在回调等待时、完成后分别完整 GC，记录相对基线的保留堆增量；4096 字节间隔的分配采样包含已回收对象和测试框架开销，不能当作精确累计分配。以下都是七次结果的中位数，内存单位 KiB，CPU 单位毫秒。

| 场景 | 等待时保留堆 v6 → v7 | 完成后保留堆 v6 → v7 | 采样分配 v6 → v7 | CPU 时间 v6 → v7 |
| --- | ---: | ---: | ---: | ---: |
| 只更新实况（对照） | 576.9 → 577.1 | 632.7 → 633.3 | 1154.1 → 1126.5 | 9.99 → 9.95 |
| 更新实况、保留 273 小时预报和 4 条预警 | 787.0 → 778.4 | 824.6 → 702.8 | 1807.0 → 1665.3 | 23.43 → 16.72 |
| 48 条预警，来源失败 | 723.1 → 623.8 | 563.3 → 548.7 | 1587.0 → 1156.6 | 11.34 → 9.05 |

混合天气场景完成后保留堆减少约 14.8%，CPU 时间减少约 28.6%；预警失败场景等待时保留堆减少约 13.7%，采样分配减少约 27.1%，CPU 时间减少约 20.2%。只更新实况的对照场景 CPU 和保留堆基本持平：完成后保留堆略增 632 字节，CPU 相差不足 1%，不视为明确改善。三组样本的最终 ArrayBuffer 增量均与 v6 相同。

只编码改动项会保留原始 arena。混合样本中，v6 重建后的输出为 19,928 字节，v7 为 25,920 字节（输入 25,432 字节）；本次减少处理分配，但不保证输出二进制更小。正常已知字段的解码结果相同，未改动表中的未来字段也保持可访问。只更新实况和预警失败样本的输出长度均与 v6 相同。

## 验证与限制

CI 的 224 项回归、18 个实际压缩脚本场景和 11 个原生表达式／路由／jq 检查通过。新增验证覆盖未知小时字段保留、成功预警合并的对象隔离、等待和失败时不深复制、每条预警只取一次视图。编译产物检查还覆盖部分替换和失败时原字节保留；下载 CI ZIP 后再次运行同一组检查并校验八个文件及 SHA-256 清单。完整构建证据见 [构建验证记录](loon-build-validation.json)。

最初的 VM 检查暴露了测试框架把输入 Uint8Array 与脚本分到不同类型环境的问题：原样保留的 slot 因 instanceof 不匹配而被拒绝。测试现在共享输入字节的 Uint8Array 构造器；该修正没有更改生产代码的类型检查。测试环境仍没有 Node、WebCrypto 或宿主 TextEncoder。

每个测量样本均确认输入字节未被修改、请求与存储操作次数相同、只完成一次；可用实况确实替换成功，失败的小时预报与预警保留原内容。所有 CPU/内存结果均为桌面模拟运行，包含框架开销，不是 Loon/JavaScriptCore 的原生内存峰值、真实 iPhone 耗电或 VPN 稳定性证明。减少重复编码和对象创建有助于降低计算负担，实际省电幅度仍需设备测量。
