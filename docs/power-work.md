# WeatherKit v4 处理开销对比

2026-10-19。目标是减少天气刷新触发的脚本、重复查询、解析、对象复制与持久化写入。默认实况／AQI 60 秒、预报 180 秒、分钟降水／预警 15 秒均不延长；不是通过降低天气更新频率获得结果。

基线为已发布 v3 主分支提交 `6e5a73124e4ff7e45d263e954f365d87af5095c8`，比较真实旧源码与旧发布 bundle。优化版本加载实际生成的三个 bundle；精确 SHA-256、主机环境、全部计数和时间保存在 [power-work-measurements.json](power-work-measurements.json)。

| 固定场景 | v3 | v4 |
| --- | --- | --- |
| 一次功能列表响应启动 JavaScript | 1 次 | 0 次；改用原生 JSON Rewrite |
| 一次普通 AQI 标尺请求启动 JavaScript | 1 次 | 0 次；改用原生 URL Rewrite |
| 自定义 HK/CN 标尺加载的脚本 | 321,150 字节 | 29,703 字节 |
| 六项已持久化产品的快照读取 | 6 次 | 1 次；六项均命中 |
| 同一小时每隔 10 秒刷新一次、共六次的昨日 AQI 附加请求 | 6 次 | 1 次；沿用 180 秒有效期 |
| 同一坐标、同一明确国家的六次刷新记录写入 | 6 次 | 1 次 |
| 不替换的小时／分钟预报 | 解码、复制已选择的表，再保留原字节 | 只探测分钟表存在性，原字节透传 |

脚本字节是载入的压缩源码大小，不代表下载流量、宿主内存或耗电。响应 bundle 因增加保护逻辑略有增长，不将总仓库大小当作性能改善指标。原生 Rewrite 本身仍然消耗处理资源。

另有 273 小时、85 分钟、25,376 字节的真实 FlatBuffer 固定样本，设置为保留 Apple 数据。每版运行 45 次新模拟执行，前五次预热不计入延迟，共 40 个延迟样本；每次核对原字节、零附加请求和仅一次完成。延迟范围从编译脚本求值到异步完成，不包含 VM 创建或脚本预编译；进程 CPU 指标另含 VM 创建、预热与输出断言，不能当成相同口径的脚本时间。原始记录报告两版中位数与 p95，随 Node 版本和机器负载变化。

复现：先在锁定依赖环境运行 `npm run build:loon-cache`，再运行 `node scripts/measure-power-work.mjs`。该脚本读取本地 Git 中的固定基线，使用 Rollup 和真实数据模型，在 Node VM 内提供模拟 Loon 同步存储与 HTTP 回调，不访问真实供应商。写入 `docs/power-work-measurements.json`。原生规则检查另使用系统 `jq`，检查表达式和匹配样例，未调用真实 Loon 配置解析器。

这些结果证明固定场景减少了哪些工作，不是手机耗电百分比。真实 iPhone 的 Loon 导入、天气显示、后台耗电、CPU 峰值与 VPN 连续运行仍未验收。已配置其他 WeatherKit 的用户应只启用一个实例；默认关闭诊断和高级调试，减少额外日志。
